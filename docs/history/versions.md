# 作問方式の版の履歴

## 読む前に

作業中の記録なので、説明なしに出てくる言葉があります。

| 言葉 | 意味 |
|---|---|
| 項目、水準、問える単位 | ブループリントの1行と、その L1／L2／L3、その項目で何を問うか |
| 水準を見せる／伏せる | 審査員に、項目の水準と「問える単位」を見せるか、隠して推定させるか |
| 一次、二次 | 審査の1回目と2回目。現在の方式では、1回目が「指摘出し」、2回目が「裁定」 |
| 提案役、実装役 | 生成を2段に分けていた頃の役。出題の設計を考える役と、問題文に仕上げる役。現在は1段 |
| クリーンなコンテキスト | コマンドライン版が自動で読み込む設定やメモリ、過去のやり取りを持たせずに、モデルを呼ぶこと。逆が「汚れたコンテキスト」 |
| ゲート | LLM を使わない機械的な検査。字数、必須の欄、形式の手がかりなどを見る |
| 下振れ、上振れ | 問題が、指定の水準より軽くなること、重くなること |
| 人手裁定 | 作者が問題を1問ずつ読んで下した判断 |
| pair／tiered／single | 審査の構成の名前。pair が現在の「指摘出し → 全問を裁定」。tiered はそれ以前の、1回目で疑いの出た問題だけを2回目に回す構成。single は1回だけの構成 |
| prefix | 実行ごとに出力ファイルへ付ける目印。条件の違う実行の結果を混ぜないためのもの |
| ①〜⑪ | 審査の指摘の記号。定義は「02 作問と審査の方式」にあります |
| Sol、Luna | OpenAI の GPT 系のモデル（Codex のコマンドライン版から呼ぶ）。Sol が上位、Luna が軽量 |
| 4.3群 | 内分泌系の「甲状腺・副甲状腺」の群（23項目）。方式を比べる実験は、主にこの群で行った |
| 5時間枠 | 定額プランの利用上限。5時間ごとに更新される |


**異なる版の結果を混ぜて集計しない**ための台帳。
`research_log.py` の `PIPELINE_VERSION` と対応する。

この書式は、作者が ChatGPT と相談して決めた記録の方針による
（変更日／版／変更点／変更理由／変更前に観察された失敗／改善を期待した指標 を残す）。

版を変えるときの手順:

1. `research_log.py` の `PIPELINE_VERSION` を上げる
2. この表に1行足す（**理由と、変更前に観察された失敗を必ず書く**）
3. 前の版で採った結果と混ぜて集計しない

### 結果（2026-10-05、第1周のみ・二次は Opus＋Sol の2人。Grok は認証切れで未参加＝暫定）

| 条件 | 問 | 合計字数 中央／最大 | 第1周採用 | L1 | L2 | L3 | 採用のある項目 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 基準 v3（09-05 Opus 5→Sol 5.6）再審査 | 26 | 172／244 | 14（54%） | 6/6 | 6/18 | 2/2 | 13/23 |
| A1 Opus 5.5→Sol 6.1 | 33 | 162／258 | 15（45%） | 6/6 | 6/23 | 3/4 | 13/23 |
| A2 Sol 6.1→Opus 5.5 | 33 | 191／250 | 16（48%） | 7/7 | 7/23 | 2/3 | 13/23 |
| B Sol 6.1 1段 | 33 | 158／242 | 17（52%） | 6/7 | 8/22 | 3/4 | 14/23 |
| C Opus 5.5 1段 | 32 | 167／263 | 14（44%） | 5/6 | 6/22 | 3/4 | 12/23 |

読み取れること:

- **条件間の差は誤差の範囲**（44〜54%、2〜3問差）。担当の入れ替えも、2段か1段かも、この審査員の下では効いていない
- **文面の冗長さは再発していない**。Opus 5.5 に書かせても中央191字・最大263字（Opus 5 実装時は中央666字）
- **落ちるのはほぼL2**。棄却理由は ⑨ と ⑩ で、⑨の向きは全件「指定より軽い」（L2 の指定がL1で解ける）。
  「重すぎ」の判定は5本を通じて0件、⑪も0件、機械の印は1件
- **同じ7項目が5本すべてで棄却された**（4.3-03/06/07/13/14/18/23。いずれもL2の「AがBにつながる関係を説明できる」型）。
  生成側を替えても落ちるので、原因は生成器ではなく項目×ブリーフ×審査の組み合わせにある
- **⑩は分割と衝突している**。ブリーフは複数要素の項目を複数問に分けさせるが、審査は1問ずつ項目全体と突き合わせるので、
  分けた各問が「一部しか問えていない」で落ちる（例: 4.3-07 の2問が互いの担当部分の欠落で両方棄却）
- **新しい審査員は厳しい**。同じ基準の生成物が 09-05 の審査員では73%、今回は54%。二次で Sol 6.1 が落とす数は Opus 5.5 の約2倍で、
  Sol だけが落としたものが各条件6〜12問ある

無効にした実行: 19:32〜20:04 の初回審査は途中で Claude の利用上限に当たり、Sonnet の全件エラーが「通過」と数えられて
B=79%・C=81% と出た。この数字は誤りで、エラーを未審査として扱う修正（run_review.py）を入れてから取り直した。

見つけた別件: 2段構成では典拠（ref）が実装役に届いていない（提案ブリーフの出力に典拠の欄が無い）。
A1・A2 は ref がほぼ空、09-05 の採用分も項目IDが入っているだけ。1段生成（B・C）は全問正しい。未修正。

## 2026-10-05.3

**変更点**

- **Claude・Codex をクリーンなコンテキストで呼ぶ**（`models.py` の `CLAUDE_CLEAN_*` / `CODEX_CLEAN_*`）。審査員と生成役の両方
- Codex の応答は `-o` で最終メッセージだけを受ける（プロンプトの復唱を拾わない）
- **1段審査モード**（`REVIEW_MODE=single`）。一次のふるいを置かず、全問を二次のやり方で1回審査する。
  役は3つ: Sonnet（水準を見せる）／Luna（水準を見せる）／Luna（水準を伏せる）。Luna は安いので両方の役を担当させる（作者案）
- Luna の推論の強さは max

**変更理由・変更前に観察された失敗**

- クリーンなコンテキストのつもりの審査員が、実測では、コマンドライン版が自動で読み込む設定を背負っていた。
  Claude は約5万トークン（利用者の指示ファイル、メモリ、スキルの一覧、MCP とツールの定義）、Codex は約2.2万トークン（指示ファイル、MCP）。
  ルーブリック本体は2〜3千トークン。**09月の375問も、10-05.1／.2 の結果も、この状態で採った判定**
  → Claude は約770トークン、Codex は審査1回あたり約1.2万トークン（ルーブリック込み）まで落ちた
- 一次の Sonnet 5.5 は33問中26〜29問に印を付け、ふるいとして働いていなかった。
  2段にした目的は上位モデルの枠の温存で、安いモデルに二次のやり方をさせるならふるいは要らない
- 二次で Sol 6.1 が落とす数は Opus 5.5 の約2倍。内訳を見ると**差は主観的な基準（⑨水準・⑩網羅）だけ**で、
  客観的な基準（①事実誤り・②選択肢曖昧）は Opus 1件・Sol 2件と差が無い。
  水準を見ない Luna が「指定より軽い」と推定した割合は、Opus と Sol の両方が⑨とした問題で 12/22・6/10、
  **Sol だけが⑨とした問題では 6/34・4/16**（どちらも⑨としなかった問題は 3/63・1/38）。

**変更点**（方式＝ブリーフ・ルーブリック・集約の規則・モデルは .4 のまま。全範囲実行で見つかった不具合の修正）

- `run_gen.py` の `normalize_questions()`（`call_json` から呼ぶ。`run_regen.py` も同じ `call_json` を通る）:
  生成の応答を JSON にした直後、ファイルへ保存する前に `questions` を正規化する。
  `item_id` が無い要素で、直前の要素に `ans` が無ければ、直前の要素へ合流させる（割れた出力の復元）。
  そのうえで `item_id`,`q`,`A`〜`E`,`ans` がそろっているか確かめ、欠けた問題が1つでもあれば呼び出しを失敗として扱う
  （既存の JSON 取り出し失敗と同じ経路。呼び直し、尽きれば生成物ファイルを書かず、次の起動でその分だけやり直す）
- `research_log.py` の `log()`: 1行ぶんを先に組み立て、`threading.Lock` の中で1回の書き込みで追記する（改行は `\n` 固定）。記録の形式は不変
- `PIPELINE_VERSION` を `2026-10-08.1` に

**変更理由**（全範囲実行で観察された事故）

- 3.4群: モデルが1問を2つの波括弧に割って出力し、後半に `item_id` が無いまま `generated_*.json` に保存。
  `run_review.py` が `KeyError: 'item_id'` で落ち続けた（保存済みファイルは再利用されるので、やり直しても直らない）
- 00_総論: 複数スレッドが同時に `research_log.jsonl` へ追記し、行が混ざって JSON として読めない行ができた
- 2.2群: 生成の呼び出し1本（Opus）が約50分応答せず、その間ずっと群全体が待たされた。
  生成1回のタイムアウトは `sol_call.py` で既に15分（900秒）だが、実際には効いていなかった疑いがある（原因は調査中。この版では変更していない）
