# 03 全範囲の実行記録

ブループリントの全50群・2,890項目に対して、[02 の方式](02_作問と審査の方式.md)を通した記録です。
このページの数字は、審査結果のファイルと呼び出しの記録から、スクリプトで直接集計しました（元データは [data/stats.json](data/stats.json)、群ごとの表は [data/groups.md](data/groups.md)）。

## 規模と時間

| | |
|---|---|
| 期間 | 2026年10月6日 22:47 〜 10月8日 09:01（約34時間。利用上限の待ち31分と、並列数を変えるための停止2回を含む） |
| 対象 | 12系統・50群・2,890項目 |
| 並列 | 同時に7〜8問を処理。モデルの同時呼び出しは Claude 9〜10本、Codex 10本まで |
| 1項目あたり | 約0.7分（群ごとの所要の合計は約33.7時間） |
| 最大の群 | 神経系の中枢神経（165項目）で160分 |

1台のパソコンから、Claude と Codex のコマンドライン版を、定額プランの利用枠で呼び出しています。API の従量課金は使っていません。

## なぜ棄却されたか

棄却は3周の合計で 1,386件です。

**経路**

| 経路 | 件数 |
|---|---|
| 客観的な指摘（事実・一意性・設問・解説・日本語）が1者以上 | 911 |
| 主観的な指摘（誤答が弱い・水準のずれなど）で2者が一致 | 373 |
| 控訴審で棄却（誤答が弱い 56、水準が違う 35） | 91 |
| 機械検査 | 11 |

**指摘の種類**（棄却とした審査員が挙げた記号。1問に複数あり）

| 記号 | 中身 | 件数 |
|---|---|---|
| ④ | 解説が不適切 | 689 |
| ⑨ | 水準のずれ | 582 |
| ① | 事実誤り | 308 |
| ② | 正解が一意でない | 302 |
| ⑥ | 誤答が極端に弱い | 180 |
| ⑤ | 日本語が不適切 | 77 |
| ⑩ | 出題意図からの逸脱 | 23 |
| ③ | 設問が不明瞭 | 20 |

最大の理由は、設問や正解ではなく **解説** でした。とくに、誤答を退ける説明の「〜だけ」「必ず」「すべて」といった断定が、例外を指摘されて落ちています。

## 審査員はどれくらい一致したか

**指摘出し**（1問につき4回。7,278問）

| 担当 | 「問題あり」とした割合 |
|---|---|
| Sonnet（水準を見せる）1回目／2回目 | 39.1%／38.7% |
| Luna（水準を伏せる）1回目／2回目 | 8.5%／8.5% |

4回のうち「問題あり」が0回だった問題は48%、1回が16%、2回が31%、3回が4%、4回すべてが1.5%でした。
同じモデルの1回目と2回目は、割合としてはほぼ同じです。モデルが違うと、4倍以上の開きがあります。

**裁定**（1問につき2者）

| 担当 | 「問題あり」とした割合 |
|---|---|
| Sonnet | 8.1% |
| Luna | 30.5% |

指摘出しでは Sonnet が厳しく、裁定では Luna が厳しい、という逆転が起きています。
指摘出しの Luna には項目の水準を伏せ、裁定では見せているので、条件が同じではありません。ただ、どちらのモデルが「厳しい審査員」かは、役と見せる情報で入れ替わる、ということは言えます。

**控訴審**（主観的な指摘で裁定が割れた 1,031問）

| 裁定 | 件数 |
|---|---|
| 問題なし（採用） | 940（91%） |
| 誤答が弱い（棄却） | 56 |
| 水準が違う（棄却） | 35 |

割れた問題の9割は、3人目の判断で採用になっています。「片方が主観的な指摘を出したら棄却」という決まりにしていたら、約940問を余計に落としていたことになります。

## 呼び出しとトークン

| 役 | モデル | 呼び出し | 失敗 | トークン |
|---|---|---|---|---|
| 生成・再生成 | Claude Opus 5.5 | 2,164 | 78 | **未計測** |
| 指摘出し・裁定 | Claude Sonnet 5.5 | 22,345 | 351 | 2,135万（出力 2,131万） |
| 指摘出し | GPT-6 Luna | 14,533 | 1 | 4,561万（入出力の合計） |
| 裁定 | GPT-6 Luna | 7,268 | 3 | 7,542万（入出力の合計） |
| 控訴審 | Claude Opus 5.5 | 1,053 | 1 | 86万（出力 86万） |

- 生成のトークンは、呼び出しの経路が使用量を返さない作りで、記録できていませんでした。
- Claude の入力の記録は極端に少なく（Sonnet で計4.4万）、実際に読ませた量を表していません。記録の取り方に抜けがあるとみていますが、原因は確かめていません。出力には、答えを出す前の思考のぶんが含まれているとみられます。
- Codex は合計だけが取れます。Luna は推論の強さを最大に設定していました。
- 失敗は、応答が返らない、形式が崩れている、などです。すべて自動でやり直しています。

**API の料金に換算した参考値**: Claude のコマンドライン版が報告する換算額の合計は、Sonnet が約551ドル、Opus の控訴審が約51ドルでした。生成の Opus と、Luna のぶんは含みません。実際には定額プランの枠で実行したので、この金額を支払ったわけではありません。

## 利用枠の消費

Claude は Pro プランで実行しました。枠は「5時間ごと」と「1週間ごと」の2種類があります。

- **5時間枠**: 同時8問で、5時間あたり85〜105%を消費しました。群の大きさで揺れます（小さい群が続くと、作り直しが数問だけ残る時間が増えて下がります）。同時7問に下げても、差は揺れの範囲内でした。
- **週の枠**: 実行前の11%から、終了時に97%まで進みました。全範囲で、週の枠の約86%です。
- 上限に当たったのは1回だけです（10月8日 07:23。枠の更新を31分待って自動で再開）。

Codex の枠は、消費の割合を記録していません。上限には当たりませんでした。

## 起きた問題と対処

| 起きたこと | 影響 | 対処 |
|---|---|---|
| 生成の AI が、1問を2つのかたまりに割って出力した。後半に項目番号が無く、審査のスクリプトがエラーで止まり続けた | 1群が「要確認」で飛ばされた | 割れた2つを1問につなぎ直して再実行。その後、生成の直後に割れを直し、必須の欄を確かめる検査を追加 |
| 生成の呼び出し1本が約50分応答しなかった | その群の進行が約50分止まった | 自動のやり直しで通過。待ち時間の上限が効いていなかった原因は未解明 |
| 上限ではないのに、審査の呼び出しの一部が応答しない。審査のスクリプトが異常終了する | 各群で散発。数分の遅れ | 見張り役が利用枠の状態を確かめてから、同じ群を続きからやり直す作りで吸収 |
| 呼び出しの記録に、壊れた行が52行できた | 集計時に読めない行が出る（問題そのものには影響なし） | 並列の同時書き込みが原因。1行を1回で書き、排他する形に修正 |
| 生成された問題の正解が A に偏っていた（63%） | そのまま出すと、A を選ぶだけで当たる | 載せるときに選択肢を並べ替えて均等化。解説が選択肢を記号で指している30問は並べ替えていない |
| 正解の選択肢について、「なぜ正しいか」の欄が空の問題が16問あった | 表示が欠ける | 「解説を参照」の一文で補った |
| 作り直しのとき、AI が中身のない応答（出力形式の説明のおうむ返し）を返した | その問題は実際には試されていなかった | 気づいてやり直した。埋め草を検査で弾く修正は未実施 |

途中で止まっても続きから再開できるよう、どの工程も結果をファイルに残してから次へ進む作りにしていました。34時間の実行で、人が手でデータを直したのは最初の1件だけです（ほかに、並列数の調整で2回、群の区切りで止めて再開しています）。

## やってみて分かったこと

- **並列を増やしても、定額の枠が先に尽きる。** 速さを決めていたのは並列数ではなく、枠の更新の速さでした。今回の条件では、枠を使い切る少し手前に並列数を合わせるのが、いちばん速い設定でした。
- **小さな作業は、最初から群ごとに同時に走らせる。** 見直しの作り直し（49問）は、順番に回すと1時間以上かかる見込みでしたが、群ごとに同時に走らせたら数分で終わりました。
- **所要時間の見積もりは甘かった。** 事前の見込みは16〜20時間でしたが、実際は34時間でした。試験に使った群（10項目）が小さく、大きい群の作り直しの尾を見込めていませんでした。
